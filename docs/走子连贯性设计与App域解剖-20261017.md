# 走子连贯性约束设计 + App 域错格解剖（2026-10-17）

> 背景：v38a 训练期间的两项侦察落地（用户指定聚焦"前两个"：走子连贯性 / App 域 33 错）。
> 数据来源：RecognitionTypes.kt / AssistBoard.kt 代码侦察 + v37/human_fp32 CPU 推理逐格解剖。

## 一、走子连贯性约束（手机端系统级修复，零模型改动）

### 1.1 现状盘点（侦察结论）

BoardTracker（RecognitionTypes.kt:40）现有机制：①连续 3 帧逐格一致才确认；②重开检测
（32 子开局匹配）；③子数跳变门限（真实走子 ±1 vs 噪声 ±2~3）；④movedSide 推断走子方
（数新增的启发式，AssistBoard.kt:71 有"同色换型不是走子证据"的补丁）；⑤硬合法性校验
（子数上限/双帅，AssistBoard.kt:114）。**缺失：新局面从未被校验"是否能从上一确认局面
恰好走一步合法移动到达"**——象棋规则里最强的结构先验被浪费了。

### 1.2 设计：确认时刻的单步匹配修正

在 candidate 确认时刻（candidateHits≥3，L188）加一层匹配：

```
枚举 prev 的全部伪合法走子（车马炮帅仕相兵，不管将军/照面——识别修正不需棋规级）：
  next_i = prev + 走子 i
  d_i = next_i 与 candidate 的逐格汉明距离
取 d_min 与达最小值的走子集合 M：
  d_min == 0：照旧确认（完美识别）
  d_min == 1 且 |M| == 1：确认 = prev + M[0]（修正后确认），走子方 = M[0].from 子颜色
  其余（d_min≥2 或匹配歧义）：照旧确认，行为与现状完全一致
```

- **修正条件刻意保守**：恰好 1 格差异 + 唯一走子解释。真实多格变化（摆局/换局/复盘跳转）
  d≥2 不受影响；匹配歧义（两步走子都能解释）不修；12 帧自愈（L108）继续兜底。
- **打的是最大错误形态**：漏检主导（渲染域 4~5 倍于幻觉，v38研究 §四）。典型漏检帧 =
  from 没清空（子已走但识别残留）或 to 保留被吃子——都是"恰好差 1 格"，一步匹配直接修复。
- **性能**：≤32 子 × ≤17 步 = 545 次候选 × 90 格比对 ≈ 5 万次比较，Kotlin 微秒级。
- **movedSide 升级**：匹配成功时走子方从 from 子颜色直接得出，替代"数新增"启发式
  （同色换型歧义自动消失）。
- **开关与回退**：AssistConfig 加 `singleMoveRepair: Boolean = true`，关掉即回到现状。
- **实现量**：AssistBoard.kt 新增伪合法走子枚举（~80 行，Go 端 renderer.piece_moves 同款
  逻辑的 Kotlin 移植）+ BoardTracker 确认分支 ~30 行。无新依赖、不碰识别管线、合规红线无涉
  （只解读已收到的帧，无任何注入）。

### 1.3 预期与验证

- 真实域帧级精度提升（漏检被规则兜住），对 26 帧/评测集数字无影响（评测是单帧离线口径）；
  收益体现在对局中的确认速度与错误局面拦截。验证 = 模拟器跑对局（api34_phone，
  x86 可测 UI/管线）观察 UNSTABLE 减少与错误局面拦截日志。

## 二、App 域 34 错解剖（v37/human_fp32 逐格）

### 2.1 数据（.cache/app9_err_report.json + app9_err_sheet.png）

逐帧：f17=6, f18=1, f19=8, f20=2, f21=4, f22=2, f23=2, f24=4, f25=5，合计 34。

### 2.2 目检三大发现（拼图逐格确认）

**发现 1：约 1/3"错格"是评测集标签-图像错位，不是模型错**。典型组：
- f19 底排 4 连格（r9c2 相/r9c3 仕/r9c4 帥/r9c5 仕）：图上棋子清晰，真值标空或标别子——
  预测反而是对的；
- f21 r8c5/r7c7 双"炮"：图上绿底炮清晰，真值标空格；
- f19 r8c2/r8c4/r8c7、f25 r8c3：真值标有子，图上空交叉点。
  推断：这 9 帧 App 截图含走子动画瞬间（棋子视觉残留/飞行中），人工真值按逻辑局面标，
  与图像瞬间错位。**影响：App 域真实模型错误约 22 个而非 34，历史各轮的 App 域数字含
  ~10 格恒定噪声**。处置建议（待用户拍板，涉评测口径）：复核后把这些格子标 IGNORE
  （遮挡语义），基线数字重刊一次；或者保留原样并在解读时声明。

**发现 2：红马→红车（N→R）×5 是最大真错簇**（f17 r9c6 / f18 r9c1 / f19 r9c6 /
f20 r9c0 / f24 r9c1 繁体"傌"）——全部红方、多在底排、App 描边圆圈画风。v18 修过
"底排红子认成黑子"，现在残余是红方类内混淆（馬/傌 → 車/俥）。修复方向：App 画风
（描边圈+细字）+ 红马字形的定向渲染加权；查字体池中馬/傌/車/俥在描边画风下的形近度。

**发现 3：绿描边棋子系统性漏检**（f17 r8c3 卒 / r9c0 炮 / r9c1 车——绿圈白底黑字，
cnvcs 画风）。渲染器棋子描边色 = theme.line，无绿色描边变体——**渲染分布从未覆盖
"绿色描边棋子"**。修复：disc_rim 描边色加 RIM_ALT 池（含绿），一行改动级。

其余真错：UI 灰色面板遮挡（f23 r7c8，遮挡物样式可加半透明灰面板变体）、黑卒→红仕
（f25 r9c3，颜色+字类双错）、相→炮（f24 r7c4）。

### 2.3 修复清单（进 v39 数据轮）

1. 渲染器描边色变体（绿系）——一行级改动，打漏检簇
2. 红马定向加权（描边画风+馬/傌 字形+底排位置）——靶向渲染已有机制（V18_BIAS）扩展
3. 遮挡物加半透明灰面板样式
4. （待拍板）human26 标签-图像错位格 IGNORE 化 + 基线重刊
5. f19/f21 类动画瞬间的教训：今后人工标注用"走子动画结束后"的稳定帧

## 三、一页结论

- **走子连贯性**：确认时刻"汉明距离≤1 的唯一单步匹配"修正，条件保守可回退，
  直打漏检（4~5 倍主错误形态），实现 ~110 行纯 Kotlin，等点火令。
- **App 域**：34 错里 ~12 格是评测集噪声（动画瞬间错位），真错 ~22 个集中在
  红马→车 ×5 / 绿描边漏检 / UI 遮挡三簇，全部可定向修复，v39 数据轮的靶子已经明确。
