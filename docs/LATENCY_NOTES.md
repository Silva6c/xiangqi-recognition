## 端到端时间差(停稳门控版本,提交 48d9df1 之后)

一次成功走子(兵 c4→c5,选中/落子均经像素对比验证):

| 事件 | 时刻 | 相对落子 |
|---|---|---|
| tap 落子(兵 c4→c5) | 08:36:33.740 | 0 |
| rec#1:过渡帧(40 子 issue=8,识别失败) | 08:36:34.524 | +0.78s |
| rec#2:停稳帧识别成功(32 子 issue=0) | 08:36:35.482 | +1.74s |
| rec#3:确认第 2 帧识别成功 | 08:36:36.262 | +2.52s |
| board confirmed | 08:36:36.263 | **+2.52s** |
| position sent | 08:36:36.264 | **+2.52s(+0ms)** |
| suggestion received(桔库命中) | 08:36:36.270 | **+2.53s(+6ms)** |

多次进对局/走子回合的确认→转发间隔稳定为 0~24ms,建议回屏 6~13ms。

## 结论

1. **确认之后的转发链路零延迟**:board confirmed 与 position sent 同一毫秒,
   suggestion 回屏 6~13ms——"棋局一变化马上转发引擎"在识别确认瞬间即达成。
2. **走子→确认 ~2.5s** 的构成:cnvcs 走子动画 ~0.8s + 停稳等待 0.2s +
   停稳帧识别 0.35~0.47s + 确认第 2 帧(重放)0.33s + 帧间 cost×1.1 节奏。
   其中 2 帧一致才确认是防误确认(动画过渡帧可产出合法但错误的局面)的
   必要代价;单帧推理 0.3~0.6s 为模拟器速度,真机量化模型更快。
3. **停稳门控生效证据**:心跳 motionAge 精确(落子动画后 490ms 归零);
   过渡帧识别失败被 transient 记账(不退避、不烧 burst),确认两帧皆为
   停稳帧;静态期零识别零开销(心跳 motionAge 线性增长、无 rec)。
4. **本轮顺带修复**:invalidStreak>=5 熔断 + 快速路径"只检测不识别"组合
   曾造成"面板拖动/切对局后首次识别被永久锁死"的死锁(实测 flag=true、
   invalid=5 时永不恢复),已改为变化帧检出的兜底识别不受熔断,限流交给
   停稳门槛 + pacer 退避。

## 全局优化三项实测(2026-09-27 晚,提交本轮)

### 1. 开局不识别(需人为创造变化帧)——根因与修复

复现链路(启动识别→cnvcs):首帧成功(32 子)后 cnvcs 跳转主菜单,后续帧全失败
→ yoloMissStreak≥3 清角点缓存 → 连续失败退避涨至 8s 封顶;主菜单背景棋盘画
持续触发"corner box implausible"失败。用户"人为创造不同帧"= 重新触发 burst
才有快节奏——静止画面下识别节奏被残留退避拖死。

修复:
- 帧差返回变化占比(frameChangeRatio);≥0.25(切页级全屏重绘)除 requestBurst
  外再 clearBackoff——用户主动到达的新页面立即全速定位,不受此前无棋盘页面
  攒下的退避拖累;走子动画/局部刷新(<0.25)不清,防持续动画页面空转。
- 识别成功但仍未确认(candidate 累积中)时续 burst(4 帧):角点复用帧 ~180ms,
  确认链保持 300ms 级节奏(修复前 pacer 1s floor 把开局确认拖到 2s+)。

实测(修复后,点"对弈"→棋盘确认):tap→确认 3.5s(含进页动画与主菜单残帧失败),
首帧成功→确认 1.25s(burst 节奏),确认→建议 14ms(桔库)。

### 2. PC 主机端显示状态异常——根因与修复

PC 日志出现同一棋盘 w/b 走子方摆动重发(19:36:54-58 四连发):识别差分失败让
redGo 卡旧值 → 用户连按"更新棋局" → 每按一次同局面重发 → PC 重复查库/重搜/
重推建议,面板状态与悬浮窗建议被反复重置(显示状态抖动的直接来源)。

修复:scheduleAnalysis 同局面去重(lastSentFen,FEN 含走子方字段)——真变化
(走子/翻转/悔棋)必不同不受影响;重新开始识别/切换引擎清位允许重发一次补推建议。
实测:两轮确认+走子,PC 端 position 无一条重复。

### 3. 皮卡鱼推理速度慢——根因与修复

PC 端默认 depth 20 + threads=逻辑核一半(本机 20 核→10 线程),中残局单次搜索
4s+ 且常被下一手打断(PC 日志 19:36/19:37 两条进引擎局面均 4s+ 无果)。

修复(不动 PC 端 Go 代码,全部配置/默认值层面):
- 产品端 configs 配置 toml 增加 [engine]:depth=16、threads=16、hash_mb=2048;
  重启后日志确认"引擎就绪 threads=16 hash_mb=2048 multi_pv=3 depth=16"。
- 手机端默认深度档位 20→16(AssistConfig.engineDepth)。
实测:未命中库局面走子确认→PC 收到→**第一条引擎建议 101ms 到达**(搜索中
info 实时回传,MultiPV 多线随搜随更);桔库命中局面 14ms。对比修复前 4s+
且可能被打断无果。

## 换边识别两项缺陷修复(2026-09-29,模拟器实测)

## cnvcs 象棋全链路测试(2026-09-29,debug 构建实测)

#### 再实锤一缺陷:走子后识别冻结(快速路径吃帧丢弃+重放旧缓冲)

复现:cnvcs 对弈确认稳态后走子(tap 选子+tap 目标),画面已变(screencap 证实棋子
到位)而识别 2 帧后彻底静默,tick starved=false unstable=0——与第 4 节"确认链
饿死"不同形态:这次 candidate 被 SAME_BOARD 清空,饿死重放条件不再命中。
debug 存帧(assist_debug_save 触发器)对比同刻 screencap 实锤:识别管线收到的
帧停留在走子前画面。因果链:走子帧被 onImageAvailable 快速路径"只检测不识别"
的帧差消费——录屏帧取走即焚,像素未保存;停稳后 frameTick 兜底 forceCapture
acquireLatestImage 返回 null(画面已静止无新帧),只能重放 lastFrame(走子前旧
缓冲)→ 识别旧局面 → SAME_BOARD → screenChangedSinceRec 被消费 → 永久冻结。
修复:onImageAvailable 三处帧差分支(节流窗口/pendingFrame/主帧差)检出变化时
同步 imageToFrame 存入 lastFrame——变化帧稀少(走子/切页),整屏拷贝代价可接受;
此后兜底重放的内容恒为"最后变化帧",静止画面下重放语义恢复正确。
(注:与 PoseRecheck 互补——前者治"棋盘几何变了",本修复治"同一棋盘上走了子"。)

## 多轮换边实验(2026-09-29,cnvcs 打谱"翻转棋盘"+悬浮窗换边按钮)

#### 实验设计

cnvcs 打谱 → 菜单 →"翻转棋盘"= 棋盘物理翻转(FLIPPED,黑在下);悬浮窗『换边』
按钮 = 换边不翻棋盘的执色覆盖。两手段组合覆盖全部换边形态,每轮验证:局面确认
FEN、悬浮窗执色文案、轮次文案、建议(桔库/引擎)、小棋盘与箭头方向渲染。

#### 结果(全部通过,修复后)

- 实验1 翻转→FLIPPED:pose recheck drift=1442px→recaptured(棋盘从顶部挪到底部,
  8s 复检自愈)→ 确认正确 32 子开局 → 桔库"炮二平七(h2c2)✓"绿定着;小棋盘
  flipped 渲染与屏幕一致,箭头方向正确。
- 实验2 翻回→STANDARD:drift=1479px→recaptured → 32 子确认 → "我方红方/
  轮到我方走"随动恢复。
- 实验3 换边按钮往返:执黑"我方黑方/轮到对方走"(红走=对方,轮次与执色解耦
  正确)↔ 执红"我方红方/轮到我方走"。

#### 实验中发现并修复:换边覆盖残留到新局

实验1 曾出现:翻转后悬浮窗仍显示"我方红方"——此前实验用换边按钮设置的执色
覆盖(manual override)未被清除,残留到翻转后的新局。根因:覆盖清除只挂在"确认
时识别朝向与上次不同"与"悔棋"两处,翻转动画的过渡确认可能已把朝向更新掉,
正式确认不再触发清除;且回到开局的 NEW_GAME 事件未清覆盖。
修复:afterRecognition 在 NEW_GAME(回到开局,执方重新未知)时也清除执色覆盖,
回归随动判定。与"朝向变化清除"双保险。

#### 已知事项(不阻塞交付)

- 悬浮窗拖到棋盘正上方时,其左列/右列会遮挡棋盘边缘,快速路径若判定"不相交"
  直采会丢被遮挡的子(实测丢 b8/h8 双炮,30 子坏确认),拖开悬浮窗即自愈;

## 皮卡鱼算力释放与扫码提速(2026-09-30)

#### 皮卡鱼性能基线实测(只读诊断,PC 端零改动)

裸驱 library/engine/pikafish.exe(2026-09-06 版,64MiB 大网络)实测 i7-13700H:
单线程 81 万 nps;16 线程 675 万;16 线程+MultiPV3 803 万——线程横向扩展正常
(8.3x),绝对吞吐受大网络推理成本限制。PC 端运行参数 threads=16/hash=2048/
